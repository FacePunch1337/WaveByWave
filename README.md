# Wave by Wave

Первый вертикальный срез кооперативного пиратского roguelike для Unity 6.

## Получение проекта

Нужны Git, [Git LFS](https://git-lfs.com/) и Unity **6000.2.8f1**.
Перед клонированием установите Git LFS:

```sh
git lfs install
git clone https://github.com/FacePunch1337/WaveByWave.git
cd WaveByWave
git lfs pull
```

Добавьте папку проекта в Unity Hub и откройте её указанной версией редактора.
При первом запуске Unity восстановит пакеты и импортирует ресурсы.
Встроенный пакет `Packages/com.unity.netcode.gameobjects` хранится в репозитории.

Бинарные ресурсы и большие сгенерированные меши хранятся через Git LFS.
Файлы `.meta`, сцены, префабы, исходный код и настройки проекта также включены
в репозиторий. Кеши Unity, локальные сборки и выходные данные `DeltaServer`
исключены через `.gitignore`.

## Что уже работает

- `Port` — стартовая сцена с простым портом, точками будущей мета-прокачки и сетевым меню.
- Steam lobby/invite через Facepunch transport; при недоступном Steam автоматически включается локальный host.

- Owner-authoritative Rigidbody-перемещение игрока, NGO-интерполяция удалённых тел и синхронизация параметров анимации.
- Owner-камера хранится в неактивном `Camera Holder` внутри `Player.prefab` и включается только у локального владельца.
- Инвентарь на 8 слотов со стартовыми предметами: сабля, мушкет, крюк, ведро и лопата.
- Выбрасывание и подбор сетевых предметов.
- `Ocean` со Stylized Water 3 и Underwater.
- Сетевой корабль-заглушка, штурвал и общая система `MovingPlatform`: стоящий игрок фиксируется в локальной точке любой сетевой движущейся платформы, а при прыжке наследует линейную и угловую скорость точки отрыва.
- Физический корень игрока остаётся в world space, а камера и модель отображаются в системе координат опоры. Поэтому интерполяция платформы и игрока не создаёт визуального скольжения у клиентов.
- `StylizedWater3.AlignToWater` на корневом корабле задаёт равновесные высоту и наклон для упругой плавучести. Сервер рассчитывает итоговую позу вместе со столкновениями и синхронизирует её через NGO вместе со всем корпусом и коллайдерами.
- `Physics Auto Sync Transforms` включён, чтобы сетевое положение коллайдера движущейся опоры было доступно Rigidbody-мотору клиента в том же кадре. В финальной фазе KCC локальный yaw игрока сохраняется относительно палубы, а наклон его transient-позы получает текущие roll/pitch корабля. Поэтому качка переносит и точку игрока, и его rotation через одну интерполированную позу.
- Когда игрок стоит без ввода, KCC сохраняет локальную точку контакта на палубе и восстанавливает её после шага. Ошибка от вращения и ground-solver не накапливается в виде дрейфа; при ходьбе локальная точка обновляется после фактически принятого перемещения.

Чтобы новый сетевой корабль получил ту же компенсацию, его сетевой корень должен содержать `NetworkObject`, `PlatformNetworkTransform` и `MovingPlatform`; коллайдеры могут находиться на любых дочерних объектах этого корня.
- Начальная граница NGO/ECS: NGO отвечает за сессию, игроков и интеракции; массовая симуляция зарезервирована за Entities/Netcode for Entities.

Facepunch transport закреплён в `Packages/com.community.netcode.transport.facepunch`.
Steam-сокет подготавливается до запуска NGO; сессия выбирает собственный виртуальный
порт и передаёт его клиентам через данные лобби. Остановка транспорта закрывает
его соединения, сохраняя Steam API координатора для дальнейшей работы с лобби.
Повторные запуски сериализованы, а fallback ожидает полной остановки предыдущей
сессии через следующие кадры Unity. `Local Host` и `Local Connect` используют один
настроенный порт (по умолчанию `7777`), без автоматического перехода на другой.
Если порт занят, запуск хоста прекращается с объяснением в статусе. Для локального
подключения на первом экземпляре нужно включить `Local Host`, на втором —
`Local Connect`. Альтернативный порт задаётся одинаково на обоих экземплярах:
аргументом `-port 7778` в сборке или полем `localPort` координатора в редакторе.
При отсутствии ответа клиента останавливают через 8 секунд с понятным сообщением;
после подтверждения от хоста загрузку сцены контролирует штатный таймаут NGO.

## Управление

- Вид строго от первого лица; мышь управляет взглядом и поворотом персонажа.
- `WASD` — движение относительно взгляда; `Shift` — спринт; `Space` — прыжок.
- `E` — взаимодействие; у штурвала `W/S` задают ход, `A/D` поворачивают, повторный `E` отпускает штурвал.
- У якорного ворота `E` занимает ближайшую свободную ручку, `W` толкает её и поднимает якорь. Повторный короткий `E` отпускает ручку. Поднятый якорь опускается только после удержания `E` до заполнения полоски; раннее отпускание отменяет опускание.
- У бортовой пушки `E` занимает/освобождает место. Мышь или `WASD` наводят её в пределах заданных углов. Выберите ядра (стартовая ячейка `6`), нажмите `ЛКМ` для зарядки за 3 секунды, затем `ЛКМ` для выстрела. После выстрела следующий клик снова начинает зарядку; она расходует одно ядро из выбранной непустой ячейки.
- Выбранные припасы используются на `ЛКМ`: еда восстанавливает здоровье, доски на корабле ремонтируют корпус. Улучшения на корабле расходуются и повышают соответствующую характеристику. Выбранное сокровище сдаётся через `E` у корабельного сундука, увеличивая общий опыт команды.
- `1–8` — слот инвентаря; `ЛКМ/ПКМ` — основное/специальное действие; `G` — выбросить предмет.
- `Esc` — сетевое меню, приглашение Steam и переход из порта в море.

## Структура

- `Assets/_Project/Runtime/Core` — composition root и реестр зависимостей.
- `Assets/_Project/Runtime/Networking` — сессия, Steam/local transports и spawn flow.
- `Assets/_Project/Runtime/Player`, `Items`, `Ships`, `UI` — игровые feature-модули.
- `Assets/_Project/Runtime/Simulation` — граница GameObject-сети и DOTS-симуляции.

Для пересоздания прототипа: `Tools > Wave by Wave > Regenerate Vertical Slice`.

## Генератор коллизии меша

Кинематический `Ship` проверяет препятствия по треугольникам твёрдых частей модели
через `KinematicShipCollision` и геометрические запросы Unity Physics 1.4.2.
На сервере сохраняются линейная и угловая скорости. Тяга и штурвал изменяют
этот импульс с ограниченным ускорением; движение не пересоздаётся каждый тик
из направления носа. Решатель проецирует перемещение за весь тик на допустимое
движение вдоль препятствий. Нормальная реакция изменяет поступательную скорость;
угловое движение, заданное кинематическим штурвалом, сохраняется, а входящая
в препятствие дуга корпуса компенсируется смещением наружу. Контакты стен не добавляют ударных
импульсов в крен/дифферент и не отменяют плавучесть. Почти горизонтальные опорные
поверхности могут корректировать высоту. Небольшое трение допускает скольжение.
Дополнительная контактная реакция учитывает угловую дугу участвующего треугольника:
разворот с упором может создавать смещение наружу. Восстановление после пересечения
меняет позицию отдельно от скорости. Суммарная коррекция за тик ограничена
`Maximum Recovery Speed` (0,75 м/с), а не умножается на число итераций.
Касательное движение и отход допустимы при уже существующем пересечении,
если шаг не увеличивает его глубину; восстановление продолжается в следующих тиках.
Rigidbody остаётся кинематическим; это
собственный решатель движения, а не динамическая симуляция PhysX.

Плавучесть — устойчивые неявные пружины по высоте, крену и дифференту. Они
постепенно возвращают корабль к пробам воды; жёсткой установки высоты и наклона
поверх результата контактов нет. Пассажиры используют коллайдеры из префаба и KCC;
итоговая поза записывается единожды в проходе движущихся платформ.
`PlatformNetworkTransform` отправляет завершённую физическую позу KCC вместе
с временной меткой каждого физического шага и полной скоростью корпуса.
На удалённом клиенте фиксированные шаги KCC и отображение корабля отдельно
выбирают позу из одного буфера снимков; кадровая поза хоста не попадает в сеть.
Часы отображения продвигаются непрерывно, а сетевые поправки постепенно меняют
их скорость. Короткие пропуски пакетов компенсируются ограниченным прогнозом.
Камера и визуальная модель пассажира составляются из render-позы корабля и интерполированного
перемещения игрока в локальных координатах палубы. Глобальное движение корабля
не проходит через второе сглаживание камеры. Корень игрока остаётся в симуляции KCC,
а сетевые локальные координаты пассажира берутся из отображаемой позы.
Опущенный якорь тормозит горизонтальное движение, но не блокирует штурвал.
`ShipAnchorCapstan.prefab` содержит четыре ручки и поворачивающиеся вместе с ними
точки для игроков с заданными позициями ног и направлениями взгляда.
Захват плавно переводит игрока и взгляд к ручке за 0,4 секунды; длительность
настраивается через `anchorHandleApproachDuration` в `NetworkPlayerController`.
Переход идёт в локальных координатах ручки и учитывает движение корабля и ворота.
Сервер занимает ближайшую свободную точку. Ворот вращается, только если все
занявшие ручки игроки одновременно удерживают `W`: один поднимает якорь за
8 секунд, двое за 4, четверо за 2. Если хотя бы один перестаёт толкать, подъём
останавливается. Нажатие `E` у занятой ручки сразу отпускает её без полоски.
Пока хотя бы
один игрок держит ручку, можно остановить толкание без потери прогресса.
Сброс разрешён, только если никто не держит ворот. Удержание `E` у полностью
поднятого свободного якоря показывает только маленькую полоску
над воротом, всегда обращённую к камере этого игрока. Раннее отпускание отменяет
сброс. Захват ручки другим игроком также отменяет удержание сброса.
После заполнения за 1 секунду ворот вращается обратно:
полный спуск занимает 4 секунды, и якорь тормозит корабль только на дне.
Нажатие `E` во время спуска занимает свободную ручку и останавливает якорь
на текущей глубине. Поднимать нужно только уже опущенную часть; отпускание всех
ручек при промежуточном положении возобновляет спуск с сохранённой глубины.
Сроки подъёма, удержания и полного спуска настраиваются в `ShipAnchor`.
Меню останавливает толкание и отменяет незавершённое удержание; выход с ручки,
смена сцены и отключение освобождают место.
Ветер выбирает новое случайное начальное направление при каждом серверном
появлении корабля; дальнейшие повороты и интервалы используют отдельный генератор
случайных чисел, не зависящий от сидов генерации мира.

`ShipCannon.prefab` имеет отдельные повороты каретки и ствола, точку дула и место
оператора. В актуальном `Ship.prefab` установлены две пушки по бортам в средней
части корабля. Выделение корня пушки с включёнными Gizmos показывает зелёную дугу
горизонтальных ограничений и синюю дугу вертикальных. По умолчанию это ±45°
по горизонтали и от −10° до +60° по высоте. Углы, скорость наведения, время
зарядки, начальная скорость ядра и гравитация редактируются в `ShipCannon`.

`ShipCannonBattery` авторитетно хранит занятые места, заряженные ядра и таймеры.
HUD владельца показывает небольшой прицел в центре камеры. При зарядке пушки
вокруг него заполняется круговой индикатор на стандартном UI Image.
Его видит только оператор пушки. Зарядка запускается нажатием ЛКМ и не требует
удержания кнопки. Переход между ячейками с ядрами сохраняет таймер; выбор ячейки
без ядра или уход от пушки отменяет зарядку. Одно ядро списывается из текущей
выбранной ячейки только при завершении зарядки; до этого оно остаётся в инвентаре.
Взаимодействие по E сначала делает точный Raycast через прицел и проверяет
дистанцию от отображаемого положения персонажа. Луч учитывает триггеры предметов,
игнорирует собственное тело и не проходит через твёрдые препятствия. При отсутствии
цели под прицелом ищется ближайший доступный объект в пределах 1.25 м от персонажа;
радиус редактируется через `interactionProximityDistance`. Объект, на который
наведён прицел, всегда имеет приоритет перед соседними предметами. Удержание E
для сброса якоря требует прямого наведения на якорь и не использует поиск рядом.
Полёт не использует Rigidbody: `p(t) = p₀ + v₀·t + ½g·t²`, с добавлением скорости
корабля в точке дула к начальной скорости. Сервер проверяет отрезки этой
траектории через SphereCast на фиксированных отсчётах 60 Гц. Обычный путь
использует переиспользуемые буферы; переполнение плотного набора контактов
обрабатывается отдельно. Клиенты получают начальные условия и время запуска,
отображают ту же параболу на временной шкале корабля и завершают полёт только
по подтверждённому сервером попаданию. Плавучесть и движение KCC не получают
сил или отдачи от выстрела. Для воды используется `BigSplash` из Stylized Water 3;
для твёрдой поверхности — пыль и визуальные осколки без Rigidbody.

`ItemDefinition` задаёт категорию, редкость, максимальный стак, тип припаса,
силу его действия, опыт сокровища и характеристику улучшения. Старые значения
категорий сохранены, включая существующие инструменты. Припасы по умолчанию
обычные; каталог также содержит редкое тяжёлое ядро, сокровища, варианты оружия
и четыре вида улучшений. Цвета: обычный — белый, необычный — зелёный, редкий —
синий, эпический — фиолетовый, легендарный — золотой. `WorldItem` показывает
вертикальное свечение и искры соответствующего цвета, без источника света
с тенями на каждый предмет. Для своего художественного оформления можно
назначить `worldVisualPrefab`; без него используются простые формы припасов.
У размещённого в сцене `WorldItem` задаются `initialItemId` и `initialAmount`.
Готовые префабы всех 19 предметов лежат в `Assets/_Project/Prefabs/Items`:
`Cannonball`, `Cannonball_Heavy`, `Plank`, `Food`, оружие, инструменты, сокровища
и четыре улучшения. Их можно перетаскивать в сцену: тип предмета уже задан,
есть триггер подбора и NetworkObject; префабы зарегистрированы в `NetworkPrefabs`.
Модели находятся в подпапке `Visuals` и привязаны к `worldVisualPrefab` в каталоге.
Готовый префаб показывает эту модель в редакторе; изменение модели в `Visuals`
обновляет и предпросмотр, и вид предмета в игре. Свечение редкости создаётся
локально при сетевом спавне. Для стопки меняется `initialAmount`.
Предметы не используют Rigidbody, NetworkRigidbody или NetworkTransform:
сервер однократно находит поверхность и передаёт начало, конец и время
процедурного броска. После короткой дуги предмет неподвижен относительно
поверхности. На корабле координаты и rotation сохраняются относительно палубы
и отображаются через ту же конечную позу корабля, включая качку и клиентскую
интерполяцию. Единственный коллайдер — триггер для подбора, не препятствие для
игрока. Высота над поверхностью вычисляется по границам модели; её положение
лёжа настраивается через `restingEulerAngles` в описании предмета. Если поверхность
не найдена, предмет остаётся в инвентаре. Свечение и искры следуют вместе с ним.
Подбор сначала заполняет существующие стаки, затем свободные ячейки; остаток
остаётся в мире. В стартовом инвентаре 20 ядер, 5 досок и 5 единиц еды.
Сундук хранит общий опыт корабельной команды; уровень равен
`1 + floor(sqrt(experience / 100))`. Редкие варианты оружия являются предметами
каталога: механика ударов саблей и выстрелов мушкета остаётся прототипной.
`collisionSkin` (4 см) задаёт область предварительного контакта, а не запрет
движения при меньшем положительном зазоре. Для проверки углового движения
используются вершины конкретного треугольника/четырёхугольника из `DistanceHit`,
а не углы объёма участка или вершины соседнего треугольника. Начальный зазор
берётся из самого результата расстояния, чтобы погрешность восстановленной
разделяющей плоскости не превращалась в неподвижное препятствие для каждого шага.
Паруса, флаги и маркеры взаимодействий не входят в твёрдый корпус.
При необходимости состав геометрии задаётся явно в поле `Solid Geometry`.

Препятствия должны иметь включённый нетриггерный `BoxCollider`, `SphereCollider`,
`CapsuleCollider`, `MeshCollider` или `TerrainCollider` без `Rigidbody` и попадать
в `Obstacle Layers`. Слои, отключённые в матрице столкновений Unity, исключаются.
Данные моделей автоматически подготавливаются редактором перед Play Mode и сборкой;
включать Read/Write на импортированных FBX не требуется.
Повторяющиеся меши скал с одинаковым масштабом используют общую геометрию запросов.
Корпус разбит на пространственное дерево участков по максимум 8 исходных треугольников.
Точные запросы выполняются только после проверки ограничивающих объёмов участка.
Сохранённый участок контакта проверяется первым. Кэш до шести разделяющих плоскостей
ускоряет скольжение и работу в углах. Дальность запросов объёмов учитывает
радиус конкретного участка. Полный пространственный проход завершается перед
продвижением корпуса; прежний обрыв на 32 запросах, замораживавший движение,
удалён. Число итераций проекции контактных ограничений ограничено `Solver Iterations`.
При исчерпании итераций допускается только меньший шаг, прошедший тот же полный
проход геометрии; непройденное перемещение не сохраняется как фактическая скорость.
Отрицательная глубина пересечения не используется как радиус поиска broadphase:
дальность запросов остаётся неотрицательной, чтобы не скрывать соседние контакты.
Для скольжения отбрасываются пары поверхностей, разделяющая плоскость которых
сохраняет зазор на всём оставшемся движении, с учётом вращения. Это позволяет
двигаться вдоль стены без серии почти нулевых шагов приближения к контакту.

С поднятым якорем тяга вперёд появляется только при раскрытии паруса и не
зависит от направления ветра. При полностью закрытом парусе тяги вперёд нет:
сохраняются инерция, пассивный дрейф и полный отклик штурвала. Сопротивление воды
постепенно переводит оставшуюся скорость в дрейф по направлению ветра;
разворот корпуса не перенаправляет эту скорость вслед за носом. В `Ship.prefab`
скорость дрейфа — 0,35 м/с. Якорь тормозит и инерцию, и дрейф.

Базовая крейсерская скорость при полностью раскрытом парусе — 2 м/с,
ветровая прибавка — до 3 м/с, суммарный предел собственной скорости относительно
дрейфа — 5 м/с. Базовая тяга и её ускорение пропорциональны раскрытию.
Нагрузка паруса равна
его раскрытию, умноженному на `abs(dot(windDirection, sailNormal))`:
ориентированная навстречу потоку плоскость ловит больше ветра, положение ребром
почти не даёт прибавки. Эта нагрузка увеличивает целевую скорость и ускорение
тяги. Закрытый парус даёт нулевую тягу и нулевую ветровую прибавку; любое
ненулевое раскрытие даёт пропорциональную прибавку при наличии захвата ветра.
Встречный ветер не меняет знак тяги вперёд и не подавляет штурвал.
Компонент столкновений корабля не заменяет, не добавляет и не отключает коллайдеры
пассажиров. Скорость опоры берётся из фактического движения `PhysicsMover`,
без смешивания с запаздывающей скоростью качки в рендере. Ошибка получения цели
корабля удерживает платформу и записывается в Console; она не прерывает общую
фазу обновления персонажей KCC. Корабль использует Discrete в PhysX: непрерывную
проверку собственного движения выполняет геометрический решатель.
Пространственный индекс препятствий создаётся при появлении серверного корабля.
После добавления, удаления, перемещения или включения статических препятствий во время
игры вызовите `KinematicShipCollision.RefreshStaticObstacles()`; при загрузке и выгрузке
сцен индекс обновляется автоматически. Изменение геометрии самого твёрдого корпуса
после инициализации требует повторного `Initialize()`.
Предел итераций ограничивает один проход решателя; частично устранённые
пересечения могут восстанавливаться несколько тиков, не запрещая скольжение и отход.

`Tools > Wave by Wave > Physics > Generate Mesh Collision` создаёт коллизию для выбранного `MeshFilter`
или выбранной иерархии. Режим `Exact Dynamic Surface` превращает каждый треугольник исходного меша в тонкую
convex-призму, направленную внутрь объекта. Поэтому внешняя контактная поверхность точно совпадает с мешем и
остаётся допустимой для динамического `Rigidbody`. Этот режим требует правильного направления треугольников
и создаёт один PhysX shape на треугольник, поэтому предназначен для случаев, где точность важнее стоимости.

Более быстрый `Compound Convex` разбивает поверхность на небольшие convex hull и приближённо сохраняет
вогнутые детали. Старые `MeshCollider` отключаются без удаления и восстанавливаются кнопкой удаления
сгенерированной коллизии.

Режим `Exact Static` создаёт единый точный concave-коллайдер и предназначен только для статических объектов
или `isKinematic` Rigidbody: PhysX не поддерживает такой коллайдер на динамическом твёрдом теле.
